# Wire passphrase= through dump and load

## Business acceptance criteria

### Outcome

`dump` / `iter_dump` / `check_dump` / `load` / `check_load` and the Database facade
accept `passphrase=` so encrypted dumps use the same streaming passphrase path as
archives; encrypted sources without a secret report IDENTITY_REQUIRED mentioning
passphrase.

Spec: none — epics.md Story 2.2 / plan-4 Part B transfer section.

### Non-goals

Does not change the public encrypt/decrypt primitives (Story 2.1). Does not add CLI
(Story 2.3).

## Technical acceptance criteria

### Interface contracts

Add keyword `passphrase=` to dump, iter_dump, check_dump, load, check_load and
matching `Database` methods. Mutex with recipients= (dump) / identities= (load).
`_prepare` / `_Decrypting` use `encryption.decrypt(..., passphrase=)`. Update
`_Header.needs_identity` docstring to mean "needs a decryption secret".

Spec: none — plan-4 Part B; design-spec §7.3 signatures to be amended in Story 2.4.

### Error and edge case handling

recipients+passphrase or identities+passphrase → `InvalidArgumentsError`. Encrypted
head + neither secret → `Finding(Code.IDENTITY_REQUIRED, ... identities= or
passphrase=)`. No new Code in 0.2.0.

Spec: none — FR9, FR11; design-spec §6 message amend in Story 2.4.

### Observability requirements

Passphrase never in transfer logs/spans. Existing operation() spans unchanged.

Spec: none — design-spec §2.4 / §8.

### Security considerations

Same as Story 2.1; credentials to mysqldump remain via option pipe (unchanged).

Spec: none — ADR-0002 unchanged; ADR-0003 passphrase mode.

### Testability approach

dump→load round-trip with passphrase=; mutex tests; IDENTITY_REQUIRED message
assertion; facade parity.

Spec: none — plan-4 Part D.

### Existing-library check

Uses Story 2.1 encryption API only.

Spec: none — plan-4 Part B.
